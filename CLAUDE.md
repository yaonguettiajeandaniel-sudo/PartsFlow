# PartsFlow

Application interne de gestion d'atelier pour la flotte VTC de l'utilisateur (catalogue de pièces, stock, achats, devis, factures, ordres de réparation, prise en charge des véhicules, techniciens). Un seul fichier `index.html` (HTML/CSS/JS, aucun build step), déployé en statique sur **GitHub Pages** (`https://yaonguettiajeandaniel-sudo.github.io/PartsFlow/`) avec **Supabase** (Postgres + Auth + Realtime + RLS) comme backend. Voir le manuel intégré dans l'appli (Paramètres → Manuel d'utilisation) pour le détail de chaque module.

## Conventions de ce projet

- Toute modification du schéma passe par un nouveau fichier `migration-N.sql` (N croissant — le dernier est `migration-19.sql`) contenant uniquement le SQL du changement. On donne son contenu à l'utilisateur pour qu'il l'exécute lui-même dans Supabase (SQL Editor) — jamais exécuté par Claude directement (pas d'accès à la base depuis cette machine).
- `git push` est toujours fait par l'utilisateur dans son propre terminal, jamais par Claude.
- Après toute modification de `index.html`, valider la syntaxe JS avant de committer (pas de Node sur cette machine — utiliser `osascript -l JavaScript` avec `new Function(source)` sur le contenu du tag `<script>`, voir l'historique de conversation pour le pattern exact).
- Ne jamais mettre la clé `service_role` Supabase dans le code ; seule la clé publique (`sb_publishable_...`) est dans `index.html`.
- Les identifiants de connexion sont des emails fictifs `@cambouis.local` (pas de vraie boîte mail) — un changement de mot de passe se fait via l'API d'administration Supabase (curl + clé service_role dans le terminal de l'utilisateur), pas via "mot de passe oublié". Procédure détaillée dans le manuel intégré (Paramètres).

## Module Clients (suivi des virements "JET_S")

Second flux d'activité de l'utilisateur (vente/financement de véhicules à des clients par virement, distinct de l'atelier), initialement suivi via une appli tierce (captures d'écran "Détail du virement") et un Google Sheet séparé (formulaire d'intake : véhicule souhaité, offre, migration d'offre). Une première analyse ponctuelle (176 virements croisés avec ~150 clients du Sheet) a été livrée dans un doc Claude : https://claude.ai/code/artifact/3b61379a-c3fd-47a8-96ea-87b0e8540529.

**Intégré dans PartsFlow** (migration-11.sql puis 12/13/14, tables `clients`, `virements`, `modeles_vehicule`, `demandes_vehicule`) comme un onglet "Clients" normal (assignable par agent, comme les autres — pas réservé aux admins). Décisions retenues :
- Import en masse des clients existants via CSV (`CSV_SPECS.clients`, dédoublonnage par téléphone) plutôt qu'une ressaisie manuelle.
- L'attribution d'un véhicule crée un véhicule réel et lié dans la flotte `vehicules` (ou réutilise un véhicule existant non déjà attribué) — pas une entité séparée.
- Un client peut souhaiter **plusieurs véhicules, éventuellement de modèles différents** (table `demandes_vehicule`, une ligne par véhicule souhaité : modèle, coût, statut, véhicule attribué). Ses virements validés remplissent ses demandes **dans l'ordre où elles ont été ajoutées** (waterfall : la 1ère demande se remplit d'abord, le surplus va à la 2ᵉ, etc.) — c'est `allouerDemandes(clientId, demandes, virements)` dans `index.html` qui fait ce calcul et détermine, pour chaque demande, la part de fonds qui lui est allouée et la date où son coût a été atteint.
- Le coût alloué à une demande est comparé à son coût avant d'autoriser son attribution : si le montant n'est pas atteint, un agent est bloqué, un administrateur doit confirmer explicitement (`verifierMontantAttribution(allocation)`, même principe que la rupture de stock côté atelier).
- Les virements déjà répertoriés ailleurs (ex. dépouillement des captures d'écran JET_S) s'importent en masse via un import dédié (`openImporterVirements`, bouton "Importer virements (CSV)") qui rattache chaque ligne à un client par téléphone — distinct du système `CSV_SPECS` générique car il doit résoudre une relation vers une autre table.
- Suppression définitive possible depuis la fiche client (réservée aux administrateurs) pour le client entier (avec ses virements et véhicules souhaités, `on delete cascade`), et par ligne pour un virement ou un véhicule souhaité pris isolément.

Les 176 captures du dossier `VIREMENTS JET_S` ont été ré-analysées une seconde fois (transaction par transaction, pas seulement des totaux agrégés) pour produire un fichier `import-virements-complet.csv` prêt à importer, rattaché par téléphone aux clients déjà connus du Google Sheet (les 16 personnes sans correspondance fiable ou sans téléphone dans le Sheet ont une fiche provisoire dans `clients-a-verifier.csv`, à vérifier/fusionner par l'utilisateur).

**Catalogue de modèles de véhicules** (migration-13.sql, table `modeles_vehicule`) : petit catalogue nom + coût, géré depuis un bouton "Modèles de véhicules" sur l'onglet Clients (ajout/modification/suppression réservés aux administrateurs). En ajoutant un véhicule souhaité sur une fiche client (`openDemandeForm`, via le combobox partagé `mountVehiculePicker`), le choix se fait par menu déroulant basé sur ce catalogue : type et coût se remplissent automatiquement et sont en lecture seule tant qu'un modèle du catalogue est sélectionné (évite le bug initial où modifier le texte à la main ne mettait pas à jour le coût) ; l'option "Autre / personnalisé…" repasse en saisie libre pour un cas hors catalogue. En édition, si le texte déjà enregistré correspond à un nom du catalogue, il est présélectionné automatiquement — le coût affiché reste celui déjà stocké tant que l'utilisateur ne change pas activement le choix dans le menu (changer le prix d'un modèle dans le catalogue ne met jamais rétroactivement à jour les véhicules souhaités déjà enregistrés).

**Historique** : ce module a d'abord été construit avec un seul véhicule souhaité par client (coût/statut directement sur `clients`), avant d'être généralisé à plusieurs véhicules par client (migration-14.sql, table `demandes_vehicule`) car certains clients achètent des véhicules de modèles différents. La migration convertit automatiquement les anciennes fiches client (un `vehicule_souhaite`/`cout_vehicule_souhaite` par client) en une demande chacune ; les colonnes d'origine restent sur `clients` mais ne sont plus lues par l'application (sauf par l'import CSV, qui les utilise en interne pour générer la première demande d'un client importé).

**Piège découvert** : le texte importé du Google Sheet contient souvent un commentaire ("Kaiyi E5 à 16 412 €"), et la conversion SQL de la migration 14 l'a copié tel quel dans `demandes_vehicule.modele_nom` (une requête SQL ne peut pas faire le nettoyage par correspondance de texte que fait `mountVehiculePicker` côté JS) — ce qui faisait réapparaître le commentaire dans le classement "Prêts à attribuer" malgré le nettoyage déjà fait à l'affichage. Corrigé par migration-15.sql (rattache et renomme par correspondance `ilike` avec `modeles_vehicule`, uniquement pour les demandes sans `modele_id`) ; le hook d'import CSV (`openCsvImport`) fait maintenant la même correspondance avant d'enregistrer une nouvelle demande, pour que le problème ne revienne pas sur les prochains imports.

**Véhicules partagés (migration-16.sql)** : certains clients n'achètent qu'une part d'un véhicule (1/2, 1/3…), et plusieurs peuvent donc être attribués au même véhicule de la flotte. `demandes_vehicule.part_denominateur` (1, 2 ou 3) porte cette information ; côté formulaire (`mountVehiculePicker`), le coût de la part se calcule automatiquement à partir du prix catalogue divisé par ce dénominateur (même logique "jamais recalculé à l'ouverture, seulement sur un changement actif" que pour le reste du coût). L'attribution (`openAttributionForm`) n'exclut plus les véhicules déjà attribués : elle affiche qui les partage déjà (nom + part) dans le menu, et demande confirmation avant d'en ajouter un de plus, avec une alerte si la somme des parts dépasserait un véhicule entier — sans bloquer, la décision reste à l'utilisateur. Un onglet "Par véhicule souhaité" (dans `VIEWS.clients`, `drawTypes`) liste tous les véhicules souhaités groupés par type, attribués ou non, pour repérer qui pourrait partager ensemble — distinct de "Prêts à attribuer" qui ne montre que les demandes déjà financées.

Le regroupement par "type" (dans les deux onglets) n'accepte que les modèles réellement liés au catalogue (`demande.modeleId`) — `typeVehiculeCatalogue(demande, modeles)` renvoie "Non déterminé" sinon, plutôt que le texte brut d'une demande "Autre" ou d'un import mal nettoyé (ex. "Budget en dessous de 10 000 €"). Ça ne change rien à l'affichage du véhicule sur la fiche d'un client précis (`libelleVehicule`, qui garde le texte réellement saisi) — seule la classification utilisée pour regrouper plusieurs clients entre eux est concernée. `sommeVehiculesEquivalents(list)` additionne 1/part par client pour afficher le nombre réel de véhicules à commander à côté du nombre de clients, dans les deux onglets.

**Validation manuelle "prêt à attribuer" (migration-17.sql)** : un administrateur peut faire basculer une demande à plus de `SEUIL_VALIDATION_MANUELLE` (90 %) en "prêt" sans attendre le solde (`basculerPretManuel`, colonnes `demandes_vehicule.valide_manuellement`/`date_validation_manuelle`). `allouerDemandes` traite cette validation comme équivalente à un montant réellement atteint (`pret=true`), mais expose un flag `valideManuellement` distinct pour que l'UI affiche "(validé admin)" à côté de la date plutôt que de laisser croire que les 100 % ont été réellement atteints. Le bouton n'apparaît (pour un agent normal : jamais, réservé aux admins) que quand le montant alloué est déjà ≥ 90 % — sur "En attente d'attribution" (section "En cours d'accumulation") et sur la fiche client elle-même.

## Contrôles anti-vol / surveillance atelier

L'utilisateur a demandé une réflexion large sur les contrôles anti-vol côté atelier (pièces). Les trois volets techniques retenus sont tous en place :
1. **Échange standard** (migration-18.sql) — voir ci-dessous.
2. **Alerte sur comportement anormal** (technicien) — voir "Contrôle & surveillance" ci-dessous.
3. **Pièces sorties non facturées** (rapprochement financier simplifié) — voir la même section.

Les autres pistes évoquées (séparation des rôles, comptages inopinés) sont déjà couvertes par l'existant (rôles admin/agent, module Comptage stock) ou relèvent de la pratique d'usage plutôt que de code.

**Contrôle & surveillance (dans `VIEWS.dashboard`, réservé aux administrateurs — `isAdmin()`)** : deux tableaux calculés uniquement à partir des données déjà chargées (`ordres`), sans nouvelle table ni migration.
- *Pièces sorties non facturées* : liste les OR encore `ouvert` depuis plus de `SEUIL_JOURS_OR_OUVERT` (14 jours) avec des `pieces` déjà posées, valorisées avec le `prixUnitaire` figé sur chaque ligne (pas le prix catalogue courant). Un vrai "rapprochement financier" strict (stock sorti vs factures émises sur une période) a été écarté après analyse du flux réel : sous l'UI actuelle, `facture.lignes` est copié verbatim depuis `ordre.pieces` à la clôture, donc un OR clôturé ne peut structurellement pas avoir d'écart — le seul écart réel et significatif vient des OR **encore ouverts**, où les pièces ont quitté le stock sans qu'aucune facture n'existe encore. C'est cette fenêtre d'exposition (pièces sorties, rien facturé) que la liste rend visible.
- *Techniciens à vérifier* : sur `FENETRE_JOURS_TECHNICIENS` (90 jours), pour chaque technicien responsable d'au moins 2 OR clôturés, le ratio (valeur des pièces posées) / (nb d'OR clôturés) est comparé à la moyenne de tous les techniciens éligibles ; un ratio supérieur à `SEUIL_ANOMALIE_TECHNICIEN` (×1,5) fois cette moyenne fait apparaître le technicien dans la liste. Seuils volontairement en constantes en tête de `VIEWS.dashboard`, faciles à ajuster si trop bruyant ou pas assez sensible.

## Pointage des techniciens (migration-19.sql)

Nouvel onglet "Pointage" (troisième onglet de `VIEWS.techniciens`, à côté de "Techniciens" et "Synthèse mensuelle"). Décisions retenues après une question de cadrage à l'utilisateur : les techniciens n'ayant pas de compte de connexion, c'est **un agent dédié** qui pointe pour eux (un bouton "Marquer l'arrivée" par technicien actif, l'heure est saisie automatiquement — jamais tapée à la main, pour éviter la triche) ; seule l'**heure d'arrivée** est suivie (pas de départ) ; un **point mensuel** (tableau "Retards du mois", avec sélecteur de mois) sert de base pour décider d'une sanction via le statut existant du technicien (Suspendu/Licencié) — pas de mécanisme de sanction automatique, volontairement laissé à la décision humaine.

- Table `pointages` (`technicien_id`, `date`, `heure_arrivee`, `en_retard`, `marque_par`) — un pointage par technicien par jour, vérifié côté client (pas de contrainte d'unicité en base, cohérent avec le reste du projet qui gère le dédoublonnage côté JS plutôt qu'en SQL).
- `config.heure_ouverture` (défaut "08:00") et `config.tolerance_retard_min` (défaut 15) : nouveaux champs sur la fiche "Général" de Paramètres, suivant exactement le même modèle que `capaciteAtelier` déjà existant (chargés dans `state.config` au démarrage, écrits via `config/general`).
- `en_retard` est calculé au moment du clic (heure système comparée à heure d'ouverture + tolérance), pas recalculé après coup — donc changer la tolérance dans Paramètres ne modifie jamais les pointages déjà enregistrés (même philosophie que les autres valeurs "figées à l'instant T" du projet).
- Suppression d'un pointage réservée aux administrateurs (erreur de manipulation), pas de modification/édition possible — on supprime et on repointe si besoin.

**Pièces à échange standard (migration-18.sql, `articles.echange_standard`)** : case à cocher sur la fiche d'un article (`openArticleForm`) pour les pièces dont l'ancienne doit être physiquement restituée (batteries, alternateurs, compresseurs…). Quand une telle pièce est ajoutée à un OR (`openAddPieceToOr`), le flag et un `ancienneRecue:false` sont **figés sur la ligne de l'OR elle-même** (`o.pieces[i].echangeStandard`/`ancienneRecue`), pas relus dynamiquement depuis le catalogue — cohérent avec la philosophie "remplissage ponctuel" déjà utilisée ailleurs (coût des modèles de véhicules, etc.), et ça évite un aller-retour vers `articles` à chaque affichage. Sur la fiche de l'OR (`VIEWS["atelier-detail"]`), un bouton "Confirmer réception" par ligne marque `ancienneRecue:true`. La clôture de l'OR (`#closeOr`) est bloquée pour un agent tant qu'il reste une pièce échange standard non confirmée ; un administrateur peut passer outre après confirmation explicite, avec une entrée dédiée dans le journal ("Clôture OR sans restitution ancienne pièce") — même principe que la rupture de stock (devis) ou le montant insuffisant (Clients).
